# HIGH

## H1 — The contact API accepts literally any JSON body

**`web/src/app/api/contact/route.ts:38`**

```ts
const { name, email, number, location, message } = await request.json();
```

No type check, no presence check, no format check, no length cap. Every downstream use assumes strings.

**Why it matters.** `POST /api/contact` with `{}` produces: a studio notification email with `undefined` in four fields; `.replace(/{location}/g, location)` at line 48 substituting the literal string `"undefined"` into the greeting; and `to: undefined` on the auto-reply at line 111. The browser form's `required` attributes (`Contact.tsx:184`) are the only validation on the whole path, and they're bypassed by any client that isn't the form.

**Fix.** Validate at the top of the handler before any send. Zod is the conventional choice but a hand-rolled guard avoids a dependency:

```ts
const b = await request.json().catch(() => null);
if (!b || typeof b !== 'object') {
  return NextResponse.json({ error: 'Invalid request body' }, { status: 400 });
}
const str = (v: unknown, max: number) =>
  typeof v === 'string' && v.trim().length > 0 && v.length <= max ? v.trim() : null;

const name     = str(b.name, 100);
const email    = str(b.email, 254);
const number   = str(b.number, 40);
const location = str(b.location, 200);
const message  = typeof b.message === 'string' ? b.message.slice(0, 5000) : '';

if (!name || !email || !number || !location || !/^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(email)) {
  return NextResponse.json({ error: 'Please check the form and try again' }, { status: 400 });
}
```

Return 400 rather than 500 so the client can distinguish "your input was wrong" from "we broke".

## H2 — Submitted text is interpolated raw into outbound email HTML

**`web/src/app/api/contact/route.ts:63-75`** (studio notification) and **`:113-125`** (client auto-reply)

```ts
<p><strong>Name:</strong> ${name}</p>
...
<p>${message || 'No additional message provided.'}</p>
```

`name`, `email`, `number`, `location` and `message` all land unescaped inside an HTML document. Line 62 also puts `${name}` and `${location}` into the `subject`.

**Why it matters.** Anyone can post `{"message": "<a href='https://evil.example'>Click to view the plans</a>"}` and Ian receives a Flintwell-branded email containing a working attacker-controlled link. Email clients render HTML. This is a phishing vector aimed squarely at your client, and it needs no account, no token, and no skill. It is not browser XSS, so it will not show up in a web security scan — which is exactly why it survives.

**Fix.** Escape every interpolated value, or send `text:` instead of `html:` for the studio notification (nobody needs a styled internal lead email):

```ts
const esc = (s: string) =>
  s.replace(/&/g, '&amp;').replace(/</g, '&lt;').replace(/>/g, '&gt;')
   .replace(/"/g, '&quot;').replace(/'/g, '&#39;');
```

Apply to all five fields in both templates. Strip CR/LF from `name` and `location` before they enter `subject`. Longer term, React Email escapes by default and Resend supports it natively.

## H3 — The endpoint is an unthrottled relay that sends mail to an address the caller chooses

**`web/src/app/api/contact/route.ts:21, 109-127`**

`to: email` on the auto-reply is caller-supplied and unvalidated. There is no rate limit, no honeypot, no captcha, no origin check.

**Why it matters.** A script can send unlimited Flintwell-branded emails, from `inquiry@flintwell.com`, with a PDF attachment, to any address it likes — with attacker-influenced content via H2. Consequences, in order of how much they'll hurt: your sending domain gets classified as a spam source and Ian's legitimate client mail starts landing in junk; the Resend quota burns; Vercel function minutes burn; each request also re-fetches and base64-encodes the brochure (M17). Combined with H1 and H2 this is the single most serious thing in the codebase.

**Fix.** Three layers, cheapest first:

1. **Honeypot** — add a visually hidden, `tabindex="-1"`, `autocomplete="off"` field to the form; reject any submission where it's non-empty. Stops most bots for ~10 lines.
2. **Rate limit by IP** — `@upstash/ratelimit` with Vercel KV, e.g. 3 requests per 10 minutes per IP. On Vercel read the client IP from the `x-forwarded-for` header.
3. **Validate `email` before using it as `to:`** (already covered by H1).

Also consider only sending the auto-reply once the studio notification has succeeded, which is already the ordering — good.

## H4 — The dedicated contact page is the one place the email and phone don't appear

**`web/src/app/contact/page.tsx:19`**

```tsx
<Contact contactData={contactData} />
```

The homepage passes both props (`web/src/app/page.tsx:46`):

```tsx
<Contact contactData={contactData} details={siteDetails} />
```

`Contact.tsx:140` gates the entire "or reach us directly" block on `details?.email || details?.phone`. With `details` undefined, the block silently vanishes.

**Why it matters.** Someone who navigates to `/contact` from the menu is, by definition, the visitor most actively looking for a way to get in touch. They are the only visitor shown the form *without* the alternative — and the code comment at `Contact.tsx:138-139` says exactly why that block exists: *"Not everyone will fill in a form."* A prospective client who'd rather phone hits a dead end on the page built for them. This is a straightforward regression, not a design decision.

**Fix.** Fetch `SITE_DETAILS_QUERY` in the contact page and pass it through, mirroring `page.tsx:20-30`:

```tsx
const [contactData, siteDetails] = await Promise.all([
  client.fetch(CONTACT_QUERY),
  client.fetch(SITE_DETAILS_QUERY),
]);
return <Contact contactData={contactData} details={siteDetails} />;
```

## H5 — The menu overlay doesn't contain focus, and loses it on close

**`web/src/components/Header.tsx:41-56, 122-126`**

The overlay correctly uses `inert={!isOpen}` (`:125`) and Escape-to-close (`:47-49`). Two gaps remain:

1. **Focus escapes the open overlay.** DOM order is header → overlay → `<main>` → footer. Tabbing past the last overlay link (`:134`, "contact") moves focus into page content that is visually covered by the terracotta panel but is not `inert`. The user is now tabbing through invisible links.
2. **Focus is destroyed on close.** If focus is inside the overlay and Escape fires, `inert` is applied to the ancestor of the focused element. Focus falls back to `<body>` and the next Tab restarts from the top of the document.

**Why it matters.** WCAG 2.4.3 (Focus Order) and 2.4.7 (Focus Visible). For a keyboard or screen-reader user the menu becomes a place you can get lost in — the classic symptom is tabbing and seeing no focus ring anywhere on screen.

**Fix.** Two changes in the existing `useEffect` at `:41`:

```tsx
// capture opener, restore on close
const opener = document.activeElement as HTMLElement | null;
// move focus into the overlay
overlayRef.current?.querySelector<HTMLElement>('a')?.focus();
return () => {
  document.body.style.overflow = previousOverflow;
  window.removeEventListener("keydown", onKeyDown);
  opener?.focus();
};
```

For containment, either add `inert` to `<main>`/`<footer>` while the overlay is open, or promote the overlay to `<dialog>` and call `showModal()` — which gives containment, Escape, and focus restoration from the platform for free, and is the cleaner end state given the overlay is already modal in every other respect.

## H6 — No `error.tsx` anywhere, on a site where every page awaits a network fetch

**`web/src/app/`** — no `error.tsx` or `global-error.tsx` exists.

Every route calls `client.fetch` at the top level: `layout.tsx:35`, `page.tsx:22-29`, `projects/page.tsx:15`, `projects/[slug]/page.tsx:24`, `contact/page.tsx:13`, plus `SiteHeader.tsx:10` on every page.

**Why it matters.** A Sanity outage, a network blip, or a malformed document turns any page into Next's unstyled default error page. On `/projects/[slug]` — which the build confirms is rendered on demand (`ƒ`), so the fetch happens on the live request path, not at build time — this is a live-traffic failure mode, not a build-time one. The root layout still renders, so a visitor gets the Flintwell footer beneath a stack-trace-shaped error box.

**Fix.** Add `web/src/app/error.tsx` (client component, per Next's convention) with the site's chrome and a `reset()` action, and `web/src/app/global-error.tsx` as the last resort. Keep them consistent with the existing type scale.

## H7 — Project pages have no metadata of their own

**`web/src/app/projects/[slug]/page.tsx`** — no `generateMetadata` export.

Every project page inherits `layout.tsx:25-28`: title "Flintwell Interior Architecture", description "Architecturally led interior design." `/projects` and `/contact` both set their own (`projects/page.tsx:10-12`, `contact/page.tsx:8-10`); the individual project pages, the actual portfolio content, do not.

**Why it matters.** On a studio portfolio the project page is the page that gets shared, linked and searched. Right now every one of them has an identical title and description in search results and in every WhatsApp, Slack and iMessage preview. There is also no `metadataBase`, no `openGraph`, no `twitter` card, and no `opengraph-image` — so shared links render as a bare title with no image, for a business whose entire product is images.

**Fix.**

```tsx
export async function generateMetadata({ params }: Props): Promise<Metadata> {
  const { slug } = await params;
  const project = await client.fetch(PROJECT_QUERY, { slug });
  if (!project) return {};
  return {
    title: `${project.title} — Flintwell Interior Architecture`,
    description: project.tagline ?? undefined,
    openGraph: {
      title: project.title,
      images: project.mainImage
        ? [urlFor(project.mainImage).width(1200).height(630).url()]
        : undefined,
    },
  };
}
```

Add `metadataBase: new URL('https://flintwell.com')` to the root metadata so relative OG URLs resolve. The duplicate `PROJECT_QUERY` fetch is deduplicated by Next's request cache within a single render **[UNVERIFIED — not confirmed at runtime; see U2]**.

## H8 — The entire CMS boundary is `any`, which disables `strict` where it matters most

**All `client.fetch` calls** — `layout.tsx:35`, `page.tsx:22-29`, `projects/page.tsx:15`, `projects/[slug]/page.tsx:24`, `contact/page.tsx:13`, `SiteHeader.tsx:10`, `route.ts:43`

`tsconfig.json:7` sets `"strict": true`, and `tsc --noEmit` passes. It passes because `client.fetch()` without a type parameter returns `any`, so every field access on Sanity data is unchecked:

```tsx
const project = await client.fetch(PROJECT_QUERY, { slug: resolvedParams.slug });
// project.gallery, project.nextProject.slug, project.title — all `any`
```

**Why it matters.** This is the one boundary in the app where data genuinely arrives unshaped, and it's the one place the type system has been switched off. `ProjectSummary` (`SelectedWorks.tsx:9-16`) and `AboutProps` (`About.tsx:7-13`) look like they're enforcing shapes, but the values flowing in are `any`, so assignment is always accepted. Rename a field in the Studio and nothing fails until a page renders blank in production. `projects/[slug]/page.tsx:99` (`project.gallery?.length > 0`) is the tell — `any` lets a possibly-undefined value be compared with `>` without complaint.

**Fix.** Sanity ships typegen for exactly this. In `studio/`, run `npx sanity schema extract`, then in `web/` `npx sanity typegen generate` to emit `sanity.types.ts`. Then swap `groq` for `defineQuery` in `queries.ts` and the generated result types flow through `client.fetch` automatically:

```ts
import { defineQuery } from "next-sanity";
export const PROJECT_QUERY = defineQuery(`*[_type == "project" && ...`);
```

If you'd rather not add the typegen step now, the 10-minute version is hand-written interfaces plus `client.fetch<Project | null>(PROJECT_QUERY, ...)` at each call site — less correct, but it turns the null case at `projects/[slug]/page.tsx:26` into something the compiler actually knows about.

All computed from source values against the surface they sit on. **[UNVERIFIED — calculated, not measured in a browser]**

| Element | File:line | Effective colour | Ratio | Required |
|---|---|---|---|---|
| Form placeholders | `Contact.module.css:145-149` | `#1a1a1a` @ 0.32 on white → `#b5b5b5` | **2.05:1** | 4.5:1 |
| `* required` hint | `Contact.module.css:169-177` | `#1a1a1a` @ 0.5 on white → `#8c8c8c` | **3.36:1** | 4.5:1 |

**Why it matters.** WCAG 1.4.3 (AA). None of these are large text — the hint and label are `clamp(0.62rem, …, 0.72rem)`, roughly 10–11.5px, and the address is `0.92em` of a 0.7–0.82rem base. ## H10 — `npm run lint` fails

**`web/src/components/RevealGrid.tsx:31`**

```
error  Calling setState synchronously within an effect can trigger cascading renders
  react-hooks/set-state-in-effect
```

`eslint src` exits 1. `next build` still succeeds — Next 16 removed `next lint`, so ESLint no longer runs during build — but any CI step calling `npm run lint` fails today.

**Why it matters.** A red lint is a red lint: it either blocks a pipeline or, worse, gets ignored, and the next genuine error hides behind it. Note the flagged code is **deliberate** and well documented at `:14-22` — `idle` → `armed` must land in a separate render or the browser coalesces the style change and no transition runs. The rule is correct in general and wrong here.

**Fix.** Suppress it precisely, pointing at the existing rationale rather than repeating it:

```tsx
// Deliberate: see the component comment — arming must land in its own render
// or the transition never runs. React's rule can't see that constraint.
// eslint-disable-next-line react-hooks/set-state-in-effect
setState("armed");
```

The alternative worth considering later: CSS `@starting-style` now does this natively and would let the whole three-state dance collapse to a plain `IntersectionObserver` toggle. Baseline-available across current browsers, but it needs a real fallback path for older Safari, so it's a refactor, not a patch.

# MEDIUM

## M1 — `useCdn: true` while every route uses ISR

**`web/src/sanity/lib/client.ts:9`**

```ts
useCdn: true, // Set to false if statically generating pages, using ISR or tag-based revalidation
```

The comment states the rule; the code does the opposite. Every route sets `export const revalidate = 30`.

**Why it matters.** Two caches stack. Next revalidates at 30s, but the Sanity CDN serves its own cached response (typically up to ~60s), so a regeneration can pick up content that's already stale. Effective worst-case staleness is closer to 90s than 30. For a site whose selling point to Ian is "edit it in the Studio and it updates", the confusing symptom is: he edits, waits, refreshes, sees nothing, edits again.

**Fix.** `useCdn: false`. With ISR the fetch happens once per revalidation window, not per visitor, so you lose the CDN's cost benefit on a handful of requests per minute and gain correct invalidation. Pair with M2.

## M2 — 30-second revalidation everywhere, with no webhook

**`layout.tsx:8`, `page.tsx:17`, `projects/page.tsx:8`, `projects/[slug]/page.tsx:20`, `contact/page.tsx:6`**

**Why it matters.** This is a brochure site for a studio that publishes a project every few months, regenerating every 30 seconds forever. It's the wrong trade in both directions: it burns Vercel ISR regenerations and Sanity API requests continuously, *and* it still makes Ian wait up to 30s (90s with M1) after an edit. On-demand revalidation gives him instant updates and near-zero background cost.

**Fix.** Raise `revalidate` to `3600` as a safety net, then add a Sanity webhook → a revalidation route:

```ts
// web/src/app/api/revalidate/route.ts
import { revalidatePath } from 'next/cache';
import { parseBody } from 'next-sanity/webhook';

export async function POST(req: Request) {
  const { isValidSignature, body } = await parseBody<{ _type: string; slug?: { current: string } }>(
    req, process.env.SANITY_REVALIDATE_SECRET
  );
  if (!isValidSignature) return new Response('Invalid signature', { status: 401 });
  revalidatePath('/', 'layout');
  if (body?._type === 'project' && body.slug?.current) {
    revalidatePath(`/projects/${body.slug.current}`);
  }
  return Response.json({ revalidated: true });
}
```

Configure the webhook in Sanity's management console with a shared secret. Validate the signature — an unauthenticated revalidation endpoint is a cheap denial-of-wallet target.

## M3 — Project pages aren't prerendered

**`web/src/app/projects/[slug]/page.tsx`** — no `generateStaticParams`

Build output confirms: `ƒ /projects/[slug]` — server-rendered on demand, the only content route not marked `○`.

**Why it matters.** Every first visitor to a project page waits on a live Sanity round-trip before receiving any HTML. That's the page a shared link lands on, and the page where a slow first byte is most expensive.

**Fix.**

```tsx
export async function generateStaticParams() {
  const slugs = await client.fetch<string[]>(
    groq`*[_type == "project" && defined(slug.current)].slug.current`
  );
  return slugs.map((slug) => ({ slug }));
}
```

## M4 — Sanity images are optimised twice, from a 900px source

**`web/src/components/SelectedWorks.tsx:105-107`**, and the same pattern at `About.tsx:32`, `projects/[slug]/page.tsx:64, 106`

```tsx
src={urlFor(project.mainImage).width(NOMINAL_WIDTH).url()}   // NOMINAL_WIDTH = 900
fill
sizes="(max-width: 640px) 78vw, (max-width: 1100px) 50vw, 30vw"
```

**Why it matters.** Two costs. First, quality: `sizes` tells Next to build a srcset up to full device widths, but every entry is derived from a 900px source. A 30vw slot on a 2560px display needs ~1536 device pixels; it gets a 900px image upscaled. Second, cost: Sanity's CDN transforms the asset, then Vercel's image optimiser transforms it again, and you're billed for the second one.

**Fix.** Pick one optimiser. Simplest is to raise the source so Next has real pixels to work with — `.width(2000).auto('format')` — accepting the double transform. Cleaner is a custom Sanity loader so Vercel steps out entirely:

```ts
// web/src/sanity/lib/imageLoader.ts
export default function sanityLoader({ src, width, quality }: ImageLoaderProps) {
  return `${src}?w=${width}&q=${quality || 75}&auto=format&fit=max`;
}
```

Wire it via `loader` on each `<Image>`, or globally in `next.config.ts`. Note this also unblocks M5.

## M5 — The Sanity hotspot is configured but ignored

**`studio/schemaTypes/project.ts`** sets `options: { hotspot: true }` on `mainImage`, `gallery`, `sliderPlan`, `sliderReality`. **`web/src/sanity/lib/image.ts:9-11`** never calls `.fit('crop')`, and `SelectedWorks.module.css:32-37` now imposes a hard `aspect-ratio: 4 / 5`.

**Why it matters.** Ian can drag the hotspot in the Studio and nothing changes on the site. With a fixed 4:5 crop applied by CSS `object-fit: cover`, the crop is always centred — so a wide room shot loses both ends regardless of what he marks as important. The Studio is promising him control it doesn't have.

**Fix.** Let Sanity do the crop so the hotspot is honoured:

```ts
urlFor(project.mainImage).width(900).height(1125).fit('crop').auto('format').url()
```

`900×1125` is 4:5, matching the CSS box. Then `object-fit: cover` becomes a no-op safety net rather than the thing making the decision.

## M6 — Six font files load; roughly two are used

**`web/src/app/layout.tsx:11-23`**

```ts

Jost({ weight: ["300", "400"], ... })
```

A grep across every CSS module and `globals.css` finds the serif set only at `font-weight: 400` (`globals.css:78`, plus inherited body default), and `font-style: italic` only at `Contact.module.css:149` (placeholders). Every sans usage sets `font-weight: 300` — Jost 400 appears nowhere.

**Why it matters.** Cormorant is declared as 3 weights × 2 styles = 6 files; 2 are used. Jost is 2 files; 1 is used. `next/font` self-hosts and subsets, but it downloads every declared weight. That's roughly 5 unnecessary font files on first load, competing with the LCP image for bandwidth.

**Fix.**

```ts
const cormorant = Cormorant_Garamond({
  weight: ["400"], style: ["normal", "italic"], variable: "--font-serif", subsets: ["latin"],
});
const jost = Jost({ weight: ["300"], variable: "--font-sans", subsets: ["latin"] });
```

Add weights back deliberately if a design needs them. **[UNVERIFIED — a weight could be referenced from inline styles or Portable Text output I didn't trace; grep covered CSS only.]**

## M7 — The header mark ships a 512px image to render at 42–62px

## M9 — Global reduced-motion rule defeats the components' own reduced-motion handling

**`web/src/app/globals.css:109-121`**

```css
@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after {
    animation-duration: 0.01ms !important;
    transition-duration: 0.01ms !important;
  }
}
```

**`web/src/components/Testimonials.module.css:155-161`**

```css
/* Movement is the enhancement here; the cross-fade still carries the state
   change on its own. */
@media (prefers-reduced-motion: reduce) {
  .slide, .slideActive { transform: none; }
}
```

**Why it matters.** The Testimonials rule deliberately keeps the opacity cross-fade and drops only the translate — which is exactly the right call, and the comment says so. The global `!important` then forces that fade to 0.01ms, so it doesn't happen. A reduced-motion user gets a hard cut between quotes with no transition at all, which is precisely the jarring change the fade exists to prevent. The stated intent of the component is silently overridden by the reset.

This is the pattern the impeccable audit spec calls out by name: a global `0.01ms` kill that destroys useful feedback. Reduced motion means *less and gentler* motion, not zero.

**Fix.** Narrow the global rule to movement only, and let components opt into keeping their fades:

```css
@media (prefers-reduced-motion: reduce) {
  html { scroll-behavior: auto; }
  *, *::before, *::after {
    animation-duration: 0.01ms !important;
    animation-iteration-count: 1 !important;
    transition-property: transform, translate, rotate, scale !important;
    transition-duration: 0.01ms !important;
  }
}
```

That kills movement while leaving opacity and colour transitions intact. `SelectedWorks.module.css:215-230` already handles its own case correctly and is unaffected.

## Motion findings

Confirming severity on the two you already know, plus what the motion audit added.

### M23 — `transition: padding` on the header — **MEDIUM, not High**

**`web/src/components/Header.module.css:16`**

The detector's stock rationale ("layout thrash and janky performance") **overstates this case**. The element is `position: fixed` (`:2`), so its containing block is the viewport and its children are two small items — the reflow is scoped to the header subtree and does not reflow the document. That's meaningfully cheaper than the generic warning implies.

It's still a real finding: it animates a layout property for 400ms at the exact moment the user is scrolling, which is when the main thread is busiest and jank is most visible. And it's redundant — `background-color`, `backdrop-filter` and `border-color` in the same declaration already carry the state change convincingly.

**Fix (cheapest first).** Drop `padding` from the transition list and let the size change snap; the fade covers it. If you want the movement, keep the padding static and animate the children instead:

```css
.header { transition: background-color 0.4s ease, backdrop-filter 0.4s ease, border-color 0.4s ease; }
.headerScrolled .markLink,
.headerScrolled .menuButton { transform: translateY(-0.3rem); }
```

Also note 400ms exceeds the 300ms budget for UI motion; 250ms would feel more responsive here.

### M24 — `transition: width` on the mark — **MEDIUM, not High**

**`web/src/components/Header.module.css:56`**, with the target at `:35-37`

Same reasoning — scoped to fixed chrome — but slightly worse than M23, because the animated element is an `<img>`: each frame is layout plus a re-raster of the bitmap at a new size, and browsers don't sub-pixel-interpolate that smoothly.

**The obvious fix is not exact, and you should know that before applying it.** The two clamps aren't a constant ratio: `46/62 = 0.742` at the desktop cap but `34/42 = 0.810` at the mobile floor. A single `transform: scale()` can't reproduce both.

**Fix.** Set the mark to its resting size and scale from the top-left corner, accepting one ratio:

```css
.mark { width: clamp(42px, 4.5vw, 62px); transform-origin: left top;
        transition: transform 0.25s cubic-bezier(0.23, 1, 0.32, 1); }
.headerScrolled .mark { transform: scale(0.76); }
```

`0.76` splits the difference; the mark ends up ~2px off its current scrolled size at the extremes, which is not perceptible. If you want it exact, override the scale inside the existing breakpoints. Alternatively — and this is the honest recommendation — just delete the transition. The mark is 42–62px; a 400ms animated resize of something that small is detail nobody registers, and removing it costs nothing visually.

### M25 — Hover durations exceed the UI budget — **MEDIUM**

| File:line | Property | Duration | Guide budget |
|---|---|---|---|
| `SelectedWorks.module.css:41` | `transform` (image scale) | **0.7s** | ~200ms for hover |
| `SelectedWorks.module.css:63` | `background-size` (underline) | 0.55s | ~200ms |
| `SelectedWorks.module.css:88` | `opacity`, `transform` (arrow) | 0.45s | ~200ms |
| `Contact.module.css:198` | `background-size` (submit) | 0.55s | ~200ms |
| `Header.module.css:71` | `color` (menu) | 0.45s | ~200ms |

**Why it matters.** Hover is the highest-frequency interaction on the site — a visitor scanning the work grid triggers it dozens of times per visit. At 0.7s the image scale is still moving after the pointer has left, so fast scanning leaves a trail of half-animated cards. Motion this slow reads as lag, not elegance.

**Fix.** Bring hover feedback into 150–250ms and keep the long, deliberate curves for the entrance animations (`:184`, `:191`), where they're correct and genuinely good. `transform 0.25s cubic-bezier(0.23, 1, 0.32, 1)` for the image; `background-size 0.3s` for the underline draws.

### M26 — Easing values are hand-typed, not tokenised — **LOW/MEDIUM**

`cubic-bezier(0.22, 1, 0.36, 1)` appears at `SelectedWorks.module.css:41, 63, 88, 141, 159` and `Contact.module.css:77, 198, 211`. `cubic-bezier(0.16, 1, 0.3, 1)` appears at `SelectedWorks.module.css:184, 191, 199` and `Testimonials.module.css:48-49`. **Why it matters.** `globals.css` tokenises colour, spacing and tracking carefully — motion is the one system left untokenised, so it's the one that will drift as components are added.

**Fix.** Add to `globals.css:1-43` alongside the existing tokens:

```css
--ease-out: cubic-bezier(0.23, 1, 0.32, 1);

```

### M27 — Testimonial swipe uses distance only, with no drag-follow — **LOW/MEDIUM**

**`web/src/components/Testimonials.tsx:17, 38-45`**

```ts
const SWIPE_THRESHOLD = 50;
if (Math.abs(distance) > SWIPE_THRESHOLD) go(distance > 0 ? 1 : -1);
```

**Why it matters.** Two gaps against how native carousels feel. First, the quote doesn't track the finger — nothing moves during the drag, then it cuts at release, so there's no sense of direct manipulation. Second, a fast 40px flick (clearly a deliberate swipe) does nothing, while a slow 60px drag advances. Velocity is what distinguishes intent.

**Fix.** Add velocity as an alternative trigger — a small change that fixes the flick case without a rewrite:

```ts
const [touchStart, setTouchStart] = useState<{ x: number; t: number } | null>(null);
// on end:
const dx = touchStart.x - e.changedTouches[0].clientX;
const velocity = Math.abs(dx) / (Date.now() - touchStart.t);
if (Math.abs(dx) > SWIPE_THRESHOLD || velocity > 0.11) go(dx > 0 ? 1 : -1);
```

Drag-follow is a bigger change and would mean a spring — worth it only if the carousel becomes more central. **[UNVERIFIED — swipe feel cannot be judged from source; this needs a real device.]**

With ISR the value would be computed at revalidation and hydrate identically. As written, the site says "copyright 2026" from January 2027 onward. Use `new Date().getFullYear()`.

**L10 — `next/link` used for an external URL.** `Footer.tsx:44-51` wraps the Instagram link in `<Link>`. It works, but `Link`'s prefetching and client navigation are meaningless cross-origin. Use a plain `<a>`. The `rel="noopener noreferrer"` is correct. Consider a visually-hidden "(opens in a new tab)" for screen-reader users.

**L11 — "next project" can link to itself.** `queries.ts:14-17`: the `coalesce` fallback is `*[_type == "project"] | order(_createdAt desc)[0]` with no `_id != ^._id` guard. With exactly one project published, the first branch returns null and the fallback returns that same project, so the link points at the current page. Add `&& _id != ^._id` to the fallback.

**L12 — `outline: none` on form inputs.** `Contact.module.css:126`. A replacement focus indicator is provided (`:137-142`: dark border plus `box-shadow`), so this isn't a WCAG failure. But `:132-135` gives hover the *same* dark border, so hover and focus are nearly indistinguishable — a keyboard user can't tell which field is active if the mouse happens to be over another. Make focus visually distinct: keep the box-shadow for focus only, or use a 2px underline on focus against hover's 1px.

**L13 — `overflow-x: hidden` on `html, body`.** `globals.css:52-56`, with `max-width: 100vw`. This masks overflow bugs rather than fixing them, and `100vw` includes the scrollbar width on desktop — so on a page with a vertical scrollbar the body is ~15px wider than the viewport, and that overflow is then hidden. It also breaks `position: sticky` for descendants in some browsers. Remove it and fix any overflow it's currently hiding. **[UNVERIFIED — I could not determine whether anything actually overflows without a browser; removing it blind may expose a real bug, so test before shipping.]**

**L14 — `tsconfig.json` hardening.** `"target": "ES2017"` (`:3`) is dated for Next 16's browser support and forces unnecessary downlevelling. `allowJs: true` (`:5`) with no JS files in the project. Neither is harmful. Worth adding once H8 is done: `noUncheckedIndexedAccess` and `exactOptionalPropertyTypes` — both would catch real bugs in the Sanity-data code paths, and both are noisy to adopt before the fetches are typed.

## What's working

Worth saying plainly, because it's unusual: **the CSS in this project is better than most production frontends.** Specifically —

- **The comments explain the *why*, including the rejected alternative.** `Testimonials.module.css:14-18` records that a `ch`-based cap silently produced a 305px column and why `rem` replaced it. `SelectedWorks.module.css:274-278` explains why the trailing scroll padding exists. `globals.css:30-35` records that `--section-top` and `--header-clear` were conflated and what broke. This is the kind of documentation that prevents a future regression rather than describing the present.
- **`RevealGrid` degrades correctly.** `RevealGrid.tsx:14-18`: the served state is visible, and only JS arms the hidden state — so a blocked or failed script can never hide the work. That's the right default, and most implementations get it backwards.
- **The swipe track is CSS-only.** `SelectedWorks.module.css:258-290` uses native scroll-snap, keeping touch inertia, keyboard scrolling and screen-reader behaviour intact, with the peeking next card as the affordance. No JS carousel, no dots.
- **Server/client boundaries are drawn correctly.** `SiteHeader` as a server wrapper feeding the client `Header`; `ProjectBackLink` isolating `useSearchParams` behind Suspense with a considered fallback (`[slug]/page.tsx:47-58`) specifically so the page isn't opted out of static rendering. That's a subtle App Router detail done right.
- **The token system is real and used.** Four spacing tokens in `globals.css` drive every section; no per-component clamps have crept back in.
- **The build is clean.** Compiles in 2.9s, typechecks, three of four routes prerender.

The findings above are almost entirely about the layers *around* the CSS — the API, the CMS boundary, metadata, and accessibility — not the design implementation.
